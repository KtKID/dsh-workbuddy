# 同一安装包兼容两套 DSH

归属：dsh-workbuddy 的发行与宿主兼容。功能定义见 [DSH 版本兼容](../compatibility.md)。创建：2026-11-05。状态：本地验收通过，待 GitHub 发布。

## ① 需求与变更

用户明确要求一个插件版本同时兼容 DSH `0.2.1-rc.2` 和 `0.2.2-alpha.2`。本次据此统一公开版本要求、兼容回归和发布检查。比较基线为 `d400037cef029795e819fb897fc31a4651ba4177`，开始时独立仓库工作区干净。基线源码及文档可通过该 Git 提交复原。

基线插件 `0.2.0` 只声明 `0.2.2-alpha.2`；此前的本地 `0.2.0-local.1` 只声明 `0.2.1-rc.2`。本次承接功能文档的整个兼容矩阵：两套宿主安装、加载同一个包，并保留协议、审批、用量和会话语义。登录凭据处理沿用现有源码。

变化为修改兼容范围及增加同一发行包的双版本回归；[变更索引](../compatibility.md#变更记录)回指本任务。

## ② 精简技术设计

- D1：包版本升级为 `0.2.1`，`engines.dsh` 与 DSH peer 范围精确列出两套目标；Cordis 保留原有范围并加入旧版稳定依赖。入口为 `package.json`，以两套依赖的类型检查和安装包回归核对。
- D2：发布构建生成一次 `.tgz`。兼容脚本解包同一文件，在隔离目录按目标锁文件安装宿主依赖，校验安装包的版本范围，直接加载包内 `lib/`，执行现有 70 项测试。旧版测试使用 `dsh-tools` 自带执行器，新版注册独立执行器；选择仅影响测试装配。
- D3：CI 增加两套宿主矩阵，Release 依赖全部矩阵成功。README 使用最新版固定下载地址并链接兼容定义，发布说明记录检查入口。

设计依据为本轮用户要求、既有包结构及发布工作流，范围覆盖 `package.json`、锁文件、兼容脚本、测试装配、工作流和对应文档。R1 保留产品代码与验证脚本的职责边界；R2 使用现有 Zod 校验包清单和命令输入；R3 单语言流程；R4 版本要求以包清单为准，测试依赖由锁文件固定；R5 沿用 DSH 版本命名；R6 目标版本与依赖选择具名；R7 构建包到各宿主的加载流程在脚本和 CI 可追踪。TS 严格配置、ESLint、Prettier 沿用项目配置，插件产品协议和状态流保持现有实现。

## ④ 技术实现

已按 D1–D3 完成。产品 `src/` 的 18 个文件与比较基线一致。

- `package.json`、`pnpm-lock.yaml`：统一版本范围及包版本，增加测试使用的 semver 依赖。
- `scripts/verify-compatibility.mjs`：校验版本、解包同一发行包、建立隔离宿主并执行类型与 70 项回归。
- `test/support/session-runtime.mjs`、`test/fixtures/dsh-0.2.1-rc.2-lock.yaml`：双版本测试装配和旧版冻结锁文件。
- `.github/workflows/check.yml`：单一构建产物、双版本矩阵及发布依赖。
- `README.md`、`docs/compatibility.md`、`docs/releasing.md`、`docs/verification.md`：兼容定义、安装和验证说明；任务与报告记录本次交付。
- `.gitignore`：本地原始执行与覆盖数据集中在 evidence 目录，源代码仓库保存汇总和公开 CI 入口。
